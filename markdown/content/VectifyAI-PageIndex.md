# PageIndex 深度评测：当 RAG 抛弃向量数据库，反而跑出了 98.7% 的准确率
> 一句话总结：**PageIndex 是一个"无向量、纯推理"的下一代 RAG 框架——它用一棵 LLM 可直接导航的"文档树"取代了向量数据库，让大模型像人类专家一样翻目录、定位章节、追踪附录引用，在金融文档基准 FinanceBench 上打出 98.7% 的 SOTA 准确率。** 如果你的业务是财报、合同、招股书、合规文件这类"长而结构化"的专业文档，这个项目值得你立刻打开 GitHub 试一下。

## 01 背景与痛点：向量 RAG 的"四宗罪"
要理解 PageIndex 的价值，得先看看它要推翻的东西。
过去两年，几乎所有人做 RAG 都遵循同一套流水线：把文档切成 300–500 token 的小块 → 用 embedding 模型把每块向量化 → 灌进 Pinecone/Chroma/Milvus → 查询时算余弦相似度取 top-k → 塞给 LLM 生成答案。这套流程在博客、客服工单等短文本上工作得不错，但一旦遇到 200 页的年报、几十万字的技术手册，就会踩进几乎无解的坑：
- **Query 和知识空间错配**：用户问的是"意图"，向量匹配的是"字面相似度"。问"营收趋势"系统只会返回所有提到"营收"的段落，而真正有答案的那张表格可能根本进不了 top-3。
- **相似 ≠ 相关**：在 200 页财报里"operating income"出现 60 次，语义相似度对它们的打分几乎一样，但只有一处在回答你的问题。
- **硬切块撕裂语义**：金融表格的表头被切进 chunk 14，数据行落在 chunk 15，两个 chunk 单独看都莫名其妙。
- **跨文档引用是黑洞**：正文写"详见附录 G"，而附录 G 的表格和查询字面毫无相似度，向量检索**永远不会**跟着引用跳过去。
这些不是调参能解决的 bug，而是架构性的天花板。**Mingtian Zhang（Vectify AI 创始人、UCL 出身、前华为研发）和 Yu Tang 在 2025 年 9 月发布的 PageIndex，给出的回答非常激进：把整套 embedding 体系扔掉。**

## 02 核心机制：让 LLM 像 AlphaGo 一样"下棋式"读文档
### 2.1 它是怎么工作的（小白版）
用一个比喻理解：传统向量 RAG 像是把一本书撕成 500 字的小纸条，全部撒进一个巨大的池子，你提问时捞上来 5 张"字最像"的纸条。而 **PageIndex 像是一个训练有素的研究员拿到一本新书——先翻目录，锁定可能相关的章节，读下去，不够再换一章，遇到"见附录 G"就真的跳到附录 G。**
整个流程只有两步：
1. **Index（建树）**：LLM 解析 PDF 的天然结构（目录、章节、页码），生成一棵 JSON 层级树。每个节点包含 `title`、`summary`、`start_index`/`end_index`（对应物理页）、`sub_nodes`（子节点）。
2. **Retrieve（推理检索）**：查询时把这棵"目录树"直接放进 LLM 上下文（作者称之为 **in-context index**），让 LLM 自主决策：扫目录 → 选分支 → 读原文 → 判断"信息够不够" → 不够就回步骤 1 继续跳。
### 2.2 技术亮点：三个真正值得称道的设计
**① 树状索引替代向量索引（架构层面）**
不是"更好的切块策略"，而是范式替换。项目借鉴 AlphaGo 的思路：与其穷举所有可能（向量全库扫描），不如学一个"策略"智能导航。约 2500 行 Python，依赖极简（OpenAI SDK、PyMuPDF、tiktoken），没有 PyTorch、没有 FAISS、没有向量库。
**② 可解释、可追溯的检索路径（合规层面）**
每次检索都会留下完整的推理轨迹："我读了第 45–52 页，在『风险管理』→『利率风险』节点找到答案。" 这在金融、医疗、法律这种被审计的行业不是加分项，而是刚需——传统向量 RAG 给你的"top-5 相似 chunk + 余弦分数"在审计官面前根本站不住脚。
**③ 跨引用追踪（能力层面）**
官方博客给了一个让人印象深刻的案例：用户问美联储年报中"递延资产总额"，正文 75–82 页只讲了增量，第 77 页有一句"详见附录 G"。向量 RAG 在这里直接失败，而 PageIndex 的 LLM 读到这句引用后顺着树跳到附录 G，把正确的表挑了出来。
### 2.3 那个 98.7% 怎么理解？
FinanceBench 是金融文档 QA 的工业级基准，基于 SEC 10-K/10-Q 文件。**传统向量 RAG 在这个基准上普遍只能跑出 30–80%**，而 Vectify 自家基于 PageIndex 的 Mafin 2.5 系统做到 98.7%。这个数字之所以可信，是因为它背后的逻辑自洽：金融文件本来就是高度结构化的，"Q3 营业利润率"这种问题的答案就长在「财务章节 → 利润表 → Q3 → 营业利润」这条明确的路径上，树检索天然契合。

## 03 上手门槛与代码示例
### 3.1 极简安装
```bash
pip install -U pageindex
```
2026 年 8 月更新后，SDK 已经支持 **local mode**：建索引、检索、对话全部在你本机完成，只需自己的 LLM key；也可以一行代码切到 PageIndex Cloud。
### 3.2 官方 Quickstart（10 行代码跑通）
```python
import os
from pageindex import PageIndexClient
os.environ["OPENAI_API_KEY"] = "your-openai-key"
client = PageIndexClient(
    index="gpt-5.6-luna",   # 建索引用的模型（基础款即可）
    chat="gpt-5.6-sol",     # 检索/对话用的模型（越强越好）
)
doc_id = client.submit_document("report.pdf")["doc_id"]
answer = client.chat("What was the 2023 operating margin?", doc_id=doc_id)
print(answer)
```
模型选型上官方有明确建议：**`index` 用基础模型就够了**，因为树结构主要靠文档 layout 抽取，LLM 只负责摘要和精炼；**`chat` 则要尽量用最强模型**，因为整棵树的搜索质量直接由它决定。
### 3.3 索引成本实测（官方 benchmark）
- 本地建索引约 **$0.001/页**（gpt-5.6-luna），一本 1000 页教材成本约 1 美元、几分钟建完，且**一次性投入，后续查询复用**。
- 9–1098 页的基准文档，索引时间在 **13 秒到 4.5 分钟**之间线性扩展。
- 对比"整个 PDF 直接塞给模型"的暴力方案：52 页文档下原生输入贵 **2.1 倍**，420 页文档下贵 **16.6 倍**，805 页以上根本塞不进上下文。
### 3.4 MCP / Agent 集成
PageIndex 提供官方 MCP server（Cloud 版），可以直接挂到 Claude Desktop、Cursor 或任何 MCP 客户端上，让 Claude 通过 `submit_document`、`search`、`chat` 等工具自主调用。对做 Agent 开发的同学来说，这是把它接到现有工具链最顺滑的路径。

## 05 竞品横向对比
| 维度 | **传统向量 RAG**<br>(LlamaIndex+Pinecone) | **GraphRAG**<br>(Microsoft) | **RAPTOR** | **PageIndex** |
|---|---|---|---|---|
| 索引结构 | 向量 | 知识图谱 | 层次摘要树 | 文档结构树 |
| 检索方式 | 余弦相似度 | 图遍历 + 社区摘要 | 层次聚合 | LLM 树上推理 |
| 是否切块 | 强制切 | 强切 + 抽实体 | 递归聚合 | **不切，按章节** |
| 可解释性 | 弱（相似度分数） | 中 | 中 | **强（完整推理轨迹）** |
| 跨文档引用 | 几乎不可能 | 强（实体关系） | 一般 | **强（沿树追踪）** |
| 查询延迟 | 毫秒级 | 秒级 | 秒级 | 秒级（多次 LLM 调用） |
| 查询单次成本 | 低（向量查询近乎免费） | 中 | 中 | **高（每次查询都调 LLM）** |
| 多文档扩展性 | 极强（亿级） | 强 | 中 | **弱（仍在演进）** |
| 适合文档类型 | 短文本、非结构化 | 关系密集型语料 | 学术/技术 | **长而结构化的专业文档** |
简单一句话定位：**向量 RAG 是"广撒网"，GraphRAG 是"建关系网"，PageIndex 是"翻目录"**。三者不是替代关系，而是互补——很多生产系统已经在做"向量粗筛 + PageIndex 精读"的混合架构。

## 06 局限与不足：评测必须直说的部分
客观地说，这个项目远非完美，以下几个坑在选型前必须想清楚。
**① 完全依赖 LLM API，两头都要花钱**
传统向量 RAG 在 embedding 阶段花一次钱，之后查询近乎免费；PageIndex 在**建索引时**和**每次查询时**都要调 LLM。一篇 100 页的 PDF 建索引要 50–200 次 API 调用（约 $0.5–5），高频查询场景下成本会迅速失控。
**② 延迟天然更高**
向量查询毫秒级返回；PageIndex 的"读树→选分支→读原文→判断够不够→可能再跳"这条推理链是**秒级**的。对交互式聊天（用户期待亚秒响应）是硬伤，对批处理和分析类任务则可接受。
**③ 强依赖文档的结构质量**
文档越"规整"（有清晰目录、标题层级），树越好建；反之，邮件线程、Slack 导出、客服工单这种没有天然层级的内容，树状隐喻就开始失效，回退到纯 LLM 分割，又慢又不稳。
**④ 基准偏科，泛化能力未证**
98.7% 的成绩来自 FinanceBench——一个**专门考金融文档**的基准，而金融文件恰恰是最结构化的文档类型之一。技术文档、法律合同、学术文献、混合媒体、非英文文档上的表现，目前缺乏公开数据。**一个 stellar benchmark ≠ 通用优势。**
**⑤ 数据主权问题（企业必读）**
本地模式虽然代码开源（MIT），但每次查询仍需把文档片段发给 OpenAI。对 HIPAA、SOC 2、金融合规环境来说，把原始文档送第三方 API 可能直接不符合规定。企业落地需要走 Vectify 的 VPC/On-premise 部署方案（需商务对接）。
**⑥ 多文档扩展尚未完全解决**
Pinecone 能扛亿级文档，但 PageIndex 的"为每篇文档建一棵树"在海量语料下如何决定"先搜哪棵树"是个未竟难题。官方 2026 年推出的 **PageIndex File System**（文件级树索引层）就是冲着这个问题去的，但成熟度仍待观察。
**⑦ "Reasoning"这个词略有营销成分**
严格说，PageIndex 做的是"LLM 读 JSON 树 + 逐层决策"，和 AlphaGo 的蒙特卡洛树搜索（带价值网络和探索-利用权衡）不是一个量级的东西。它更像**结构化 prompting** 的极致化，理解这一点能帮你更准确地预估它的能力边界。

## 07 结语与行动建议
**这是一篇高分但需要"场景匹配"的项目。**
PageIndex 的真正价值不在于"取代向量 RAG"，而在于**戳破了一个行业迷思**：chunking + embedding 不是 RAG 的物理定律，只是工程惯性。它用不到 3000 行代码、一份 FinanceBench 98.7% 的成绩单，证明了对结构化长文档而言，"让 LLM 像人一样翻目录"是更优解。
如果你符合以下任一条件，**值得今天就 clone 下来跑一遍**：
- 业务核心是财报、招股书、合同、合规文件、技术手册
- 被向量 RAG 的"相似但无关"检索结果折磨过
- 需要**可追溯、可审计**的检索路径（金融/医疗/法律）
- 在做 Agent，需要给模型一个能"读懂长文档"的工具
如果你属于以下场景，**建议继续用向量 RAG 或混合方案**：
- 亿级文档、高并发、亚秒响应
- 文档本身无结构（聊天记录、工单、邮件）
- 每查询成本预算极低（< $0.001）
- 数据不能出本地且无企业版预算
**一条务实的落地路径**：先用 PageIndex 处理占业务价值 80% 的"少数关键长文档"，让向量 RAG 继续承担"海量短内容粗筛"，两者通过 router 组合——这可能是 2026 年最务实的 RAG 架构。
