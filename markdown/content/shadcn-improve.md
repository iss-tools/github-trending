# shadcn/improve 深度评测：把"贵的脑子"和"便宜的手"拆开用
**一句话总结**：shadcn/improve 是 shadcn（shadcn/ui 作者）推出的一个 AI Agent Skill，它用一个"只读不改代码"的硬约束，让最强模型去理解代码库、写出可被任何便宜模型直接执行的实施计划（Plan），把"贵的智力"和"便宜的手"彻底拆开——如果你想用 AI 长期维护一个真实工程，这是目前最值得装的一个 Skill。
---
## 一、它到底是个什么东西
先用人话讲清楚定位，免得小白被"Agent Skill"这种词劝退。
**它不是软件，也不是库，而是一份精心写好的"提示词说明书"**（一个 SKILL.md 文件，目前 30+ 行核心指令 + 引用的 playbook 与模板）。装到 Claude Code、Cursor 等支持 Agent Skills 格式的工具里之后，你就可以在仓库里敲 `/improve`，让它像一位高级顾问一样扫一遍你的代码库，输出一份按优先级排好的"待办清单"和一份份可以丢给任何便宜模型（甚至人类实习生）直接执行的 Markdown 计划。
它做的事可以用一行公式概括：
```
你           →  /improve           （贵模型，只动嘴不动手）
plans/       →  001-fix-n-plus-one.md （纯 Markdown 计划文件）
其他便宜模型   →  实现、测试、交付     （便宜模型，照着执行）
```
作者用了非常克制的一条**硬规则**锁死了它的行为：**永远不修改源代码**。它唯一能写入的是 `plans/` 目录下的 Markdown 文件；唯一的例外是 `/improve execute` 模式下，它会派一个"执行者子代理"在隔离的 git worktree 里改代码，然后自己审阅 diff 给出"通过 / 打回 / 阻塞"的判决——合并与否，永远是你的决定。

## 二、背景与痛点：为什么在这个时间点出现
要理解 improve 为什么这么设计，得先看两件事：**谁做的**、**为什么是 2026 年 6 月**。
### 作者背景：shadcn 本人
shadcn 是 React 生态最有影响力的独立开发者之一，他做的 shadcn/ui 在 2025 年 JavaScript Rising Stars 上再涨 2.6 万 star，总 star 数已经突破 10 万，被 OpenAI、Sonos、Adobe 等公司大量采用。他在 2025 年还把 shadcn/ui 升级成了一套"代码分发平台"——本质上是把"组件"这个概念抽象成"可被 agent 拉取的自包含文件单元"。
improve 把同样的哲学搬到了另一个层级：**组件分发给 AI，"任务"也分发给 AI**。一个 Plan = 一个自包含的工作单元，任何 agent 都能消化。这就是同一个作者一以贯之的设计思想。
### 时间点：和昂贵旗舰模型绑定的经济学
improve 在 2026 年 6 月 10 日上线，紧跟着 Anthropic 新旗舰模型发布的第二天。新模型在 SWE-Bench Pro 等基准上极强，但价格也翻倍——每百万输入 token 约 10 美元，每百万输出 token 约 50 美元。在 agentic 循环里喂 20 万 token 上下文跑一个 5 万行代码库，账单会非常难看。
shadcn 看到的核心事实是：**真正需要"高智力"的工作只是少数环节**——理解代码库、判断哪些问题值得修、写清楚规范。一旦规范写清楚了，"打字改代码、跑测试、跑验证命令"这种事一个便宜模型就能可靠完成。把 intelligence 复利的部分交给贵模型，把可机械化的部分交给便宜模型——这就是 improve 的经济学假设。
上线 48 小时拿了 1.4k star，截至 2026 年 8 月 Skillselion 统计已达到 **9,009 GitHub star、30,979 次安装**，Google Trends 90 天搜索热度涨了 180%。

## 三、核心亮点与工作流剖析
improve 的精妙之处不在于某个炫技功能，而在于它把"高级工程师做技术规划"这件事拆成了 6 个阶段，每个阶段都有明确交付物。
### 3.1 六阶段工作流
1. **Recon（侦察）**：读 README、`CLAUDE.md`/`AGENTS.md`、`package.json`、CI 配置、ADR（架构决策记录）等，搞清楚这是什么栈、用什么命令 build/test/lint、仓库里有哪些"已经决定过不要改"的取舍。**这一步的产出会变成后面每份 Plan 的"验证命令"**。
2. **Audit（并行审计）**：分九个类别并发扫描——正确性/bug、安全、性能、测试覆盖、技术债、依赖与迁移、DX 工具链、文档、产品方向。每条发现必须带 `file:line` 证据、影响评估、工作量估计（S/M/L）、风险、置信度——**"凭感觉"的发现一律拒绝**。
3. **Vet（复核）**：作者深知子代理容易"过度上报"，所以要求主顾问**亲自打开每一条引用的代码**，剔除三类错误：被误判的"按设计行为"（例如把 `https_proxy` 标成 SSRF）、张冠李戴的证据、跨子代理的重复项。被拒绝的发现会写进 `plans/README.md`，下次审计不再重复打扰你。
4. **Prioritize（排序）**：按"影响力 ÷ 工作量 × 置信度"排序，**"产品方向"类建议单独成节**——不会把"做一个插件系统"和"修一个 N+1"混在一张表里。
5. **Plan（写计划）**：每条被你选中的发现生成一份 Markdown 计划，编号 `001-<slug>.md`，配上 `plans/README.md` 作为索引（含依赖顺序、状态表）。
6. **Execute + Reconcile（执行与收尾）**：`/improve execute <plan>` 在隔离 worktree 里派便宜模型干活并审阅；`/improve reconcile` 在下次会话里清理积压——验证已完成的、刷新漂移的、解卡被阻塞的。
### 3.2 三档强度，按 token 预算选
| 模式 | 覆盖范围 | 并发子代理 | 类别数 | 发现数 |
|---|---|---|---|---|
| `quick` | 仅热点（高变更+高关键代码） | 0–1 | 3 类（bug/安全/测试） | 前 ~6 条，仅高置信 |
| `standard`（默认） | 热点加权 + 关键包 | ≤4 | 全部 9 类 | 完整表 |
| `deep` | 整个仓库、每个包 | ≤8（每类一个） | 全部 9 类 | 完整表 + 低置信待查项 |
无论哪档，它都必须**主动报告"哪些没扫到"**——这一点比很多商业审计工具都诚实。
### 3.3 一份"能让最弱模型执行成功"的 Plan 长什么样
这是 improve 最有洞察力的设计，作者用一个精确术语描述它：**"为最弱合理执行者而写"（written for the weakest plausible executor）**。一份合格的 Plan 必须同时满足四个属性：
- **完全自包含**：所有上下文都内联——精确文件路径、当前代码片段、仓库约定（带一个现有范例文件的摘录）、验证命令。执行者绝不至于"如前所述"。
- **验证门（Verification gates）**：每一步末尾跟一条命令和它的预期输出，"完成"的标准必须机器可判定，而不是"代码看起来对了"。
- **硬边界**：明确列出 in-scope / out-of-scope 文件，以及"看起来相关但绝不能碰"的内容。
- **STOP 条件 + 漂移检查**：每份 Plan 盖上写入时的 git commit 短哈希，执行者先做一次机械化的漂移检查；遇到"现实和计划不符"的情况直接 STOP 并汇报，**绝不允许小模型临场发挥**。
打个比方：improve 写的 Plan 就像一位资深架构师交给外包团队的"施工图"——精确到梁柱尺寸、材料规格、验收标准，并且写明"如果钻到钢筋，停下来打电话"。这种规格化思维正是 40 年来软件工程一直在做、但 AI 时代才被正式形式化的事。
### 3.4 一条真实发现示例（来自对 shadcn/ui 自身的审计）
improve 仓库 README 里给出的真实输出长这样：
```
| # | Finding                                          | Category   | Effort | Confidence |
|---|--------------------------------------------------|-----------|--------|-----------|
| 1 | shadow-config 在 search.ts / view.ts 重复，副本    | tech-debt | M      | HIGH      |
|   | 已经漂移（TODO 标记在 search.ts:31）              |           |        |           |
| 2 | O(n²) 图标迁移 (migrate-icons.ts:168)             | perf      | S      | HIGH      |
```
而被拒绝的发现也明明白白记录在案：
```
- [SEC-01] https_proxy 环境变量"SSRF"：按设计——标准代理约定，
  每个 CLI 都遵循。不算发现。
```
这种"明确的拒绝 + 理由"是 improve 区别于一般 AI 审计工具的关键——大多数工具的痛点是误报太多，下次扫描又把同一坨噪音甩给你。

## 四、上手指南与代码示例
### 安装：一行命令
```bash
npx skills add shadcn/improve
```
支持 Claude Code、Cursor 以及任何兼容 Agent Skills 格式的宿主。因为最终产物是纯 Markdown，**任何 agent（或人）都能接住它写的 Plan**。
### 命令面板（速查表）
| 命令 | 用途 |
|---|---|
| `/improve` | 全量审计 → 排序发现 → 写 Plan |
| `/improve quick` | 便宜扫描：只看热点、只出 top 发现 |
| `/improve deep` | 彻底扫：每个包、每个类别 |
| `/improve branch` | 只审当前分支的 diff（提 PR 前用） |
| `/improve security`（也支持 perf/tests/bugs 等） | 单类别聚焦审计 |
| `/improve next` | 只出产品方向/功能建议 |
| `/improve plan <描述>` | 跳过审计，直接为已知问题写 Plan |
| `/improve review-plan <file>` | 批改、收紧已有 Plan |
| `/improve execute <plan>` | 派便宜执行者跑一份 Plan 并审 diff |
| `/improve reconcile` | 维护积压：验证/解卡/退休 |
| `--issues` 后缀 | 把 Plan 同步发布为 GitHub Issue |
### 第一次跑的推荐姿势
```bash
# 1. 确保工作区干净（Plan 会盖 git commit 戳）
git status   # 最好无未提交改动
# 2. 在仓库根目录，先用 quick 试水
/improve quick
# 3. 看完发现表后回复，例如
plan 1, 3 and 5
# 4. 读 plans/ 里的文件，然后交给任何便宜模型
/improve execute 001
# 5. 下次会话清理积压
/improve reconcile
```
**如果你要在提 PR 前用**：`/improve branch` 会只审 branch 改动的文件和它们直接调用/被调用的文件，并把每条发现标记为 `introduced`（本分支引入）或 `pre-existing`（踩到的旧债）——不会把祖传债算到你头上，但会提醒你建立在什么之上。

## 六、同类对比：它在哪个生态位
improve 不是横空出世的孤品，但**它填补的生态位目前没有人做同样的事**。下面是和几个最容易被混淆的对象的对比：
| 工具 | 工作对象 | 时机 | 改不改代码 | 核心产物 |
|---|---|---|---|---|
| **shadcn/improve** | 整个仓库（或一个分支） | 实施前 | 永不改源码 | 自包含 Plan 文件 + 索引 |
| Claude Code 内置 Plan Mode | 单一任务 | 单任务前 | 不改（确认后才执行） | 会话内规划，不持久化 |
| Cursor Bugbot | PR diff | 实施后 | 不改 | 评审评论 |
| mattpocock / code-review | PR diff | 实施后 | 不改 | 评审报告 |
| ESLint / SonarQube 等静态分析 | 整仓库 | 任何时刻 | 部分可 auto-fix | 规则违规清单 |
| Aider / 全自主 coding agent | 整仓库 | 实施中 | 直接改 | 改后的代码 diff |
**关键差异**：
- 和"内置 Plan Mode"比，improve 的 Plan 是**持久化的 Markdown 文件**，带依赖图和状态表，可以被任何后续会话/其他 agent 接手，不依赖当初那个会话的记忆。
- 和"code review 类"比，improve 工作在**前**（决定写什么），review 工作在**后**（检查写出来的 diff），两者能串联：improve 出 Plan → 便宜 agent 实现 → code-review 检查 diff。
- 和"静态分析器"比，improve 不靠规则匹配，而是用大模型的推理力，能给出"这个迁移值得做"这种规则引擎根本无法表达的判断；代价是**单次成本远高于 lint**，且输出有概率性。

## 七、局限、风险与避坑指南
评测要客观，shadcn/improve 的光环背后有一组实打实的限制，**不踩这些坑你才能拿到它的全部价值**。
### 7.1 它的硬伤
1. **"贵模型进 → 弱计划出"**。如果你给它配的"审计模型"本身不够强，写出的 Plan 同样会让执行者翻车。Garbage in, garbage out 在这里换了个皮——"贵 model in, garbage plans out"。
2. **没有测试/CI 的仓库会让"验证门"形同虚设**。Plan 的核心安全机制是机器可校验的 done criteria，如果 `pnpm test` 本身就跑不起来，整份 Plan 的可靠性塌方。作者自己也把"建立验证基线"列为这类型仓库的发现 #1。
3. **Plan 会漂移**。代码天天在动，上个月写的 Plan 这个月可能已经引用不存在的代码。必须定期跑 `/improve reconcile`，否则积压的 Plan 反而变成新的"假信息源"。
4. **贵模型的成本不可忽视**。`deep` 模式在中等仓库上单次审计仅输入 token 就大约 $4，如果反复 deep 而不重用 Plan，省钱逻辑就不成立。**先用 `/improve quick` 试水**是官方 README 都强调的姿势。
5. **它不会救你，它只顾问**。很多用户第一次用会本能地让它"顺手把这个 bug 修了"——会被明确拒绝。这是设计而非 bug，但对期待"一键变好"的人是一种心理落差。
### 7.2 实操避坑清单
- **跑之前先把工作区提交干净**。Plan 盖的 git commit 戳一旦和现实不符，漂移检查会让所有 Plan 一次性失效。
- **不要无脑执行它写的所有 Plan**。improve 的真正价值是"排序"，把 Leverage 低的、风险大的、和产品方向不符的 Plan 直接删掉——把它当 backlog 用，不是 TODO 清单。
- **大 monorepo 上别迷信 `deep`**。即使 deep 也会把子代理 scope 到包级别而不是仓库根；与其硬跑 deep，不如按包分批跑 `standard`。
- **意图文档（ADR、CONTEXT.md、DESIGN.md）写得越好的仓库，improve 越省心**——它能识别"这是设计决定，不要再报"，减少大量误报。如果你维护的项目还没有 ADR，先补 ADR 再跑 improve，性价比最高。
- **不要在没读过 Plan 的情况下让 `/improve execute` 直接合到主分支**。它默认是隔离 worktree + 你审 diff，把"审"这一步跳过等于自废武功。
### 7.3 安全与隐私
improve 在 SKILL.md 里写了两条值得单独点名的安全设计：① 发现凭据/token 时**只引用 file:line 和凭据类型，绝不复制值本身**；② 把仓库内容视为**数据而非指令**——如果某个被读的文件里有"忽略之前的指令"这类 prompt injection，它会被识别为安全发现而不是被跟随。这两条规则还会显式复制给每个子代理，防止泄漏。这是把 prompt injection 当一等公民处理的少见设计。

## 八、结语与行动建议
shadcn/improve 值得装，但**它的价值取决于你怎么用它**。
**如果你只能记住一句话**：它是把"AI 写代码"这件事从"贵模型一路到底"的财务噩梦，重构为"贵模型写规格、便宜模型照图施工"的工程学解法——而它本身**只写规格，从不施工**。
**给不同读者的三步行动建议**：
- **已经在用 Claude Code / Cursor 且维护着真实项目的开发者**：今天就在你的主力仓库跑一次 `/improve quick`，先看它能不能挖出你不知道的问题，再决定要不要投入 `deep`。这一步几乎零成本，回报可能很大。
- **维护遗留系统或要接手陌生仓库的团队**：先花一小时补 ADR 和 CONTEXT.md，再跑 `/improve`，它的输出质量会有显著跃升；把生成的 Plan 当团队 backlog 用，配合 `--issues` 直接同步到 GitHub Issue 让人类或 agent 并行消化。
- **个人小项目 / 纯学习用途**：性价比不高。一个小脚本、一个 side project，模型一眼能看完整个仓库，没必要花一份审计的钱去产 Plan——直接用普通对话式 AI 改代码更顺手。
最后给一个**冷静的提醒**：improve 解决的不是"AI 写代码不够好"，而是"AI 写代码太贵"。如果你的痛点是前者（模型能力不够），这个工具帮不了你；如果你的痛点是后者（每次 agentic 循环烧掉几十美元），它会是 2026 年最值得装的一个 Skill——前提是，你愿意读它写的 Plan，而不是让 Plan 在 `plans/` 目录里慢慢变成数字垃圾。
